# Release rollback

Requirement ids: OPS-01, OPS-03. Env var names only; no secrets, tenant ids or customer content belong in this file or in incident notes.

1. **Decide**: roll back when a release causes a SEV1/SEV2 and a forward fix is not minutes away.
2. **Redeploy the previous Railway deployment for web and worker together** (Railway → service → Deployments → previous → Redeploy). Safe because every migration since Phase 15 passes `src/lib/db/migrations-lint.test.ts` (additive only): the old code runs on the new schema. Never run a down-migration; a bad migration is fixed forward with a new additive migration.
3. **Worker drain**: Railway sends SIGTERM; the worker stops claiming, lets the in-flight job finish within `WORKER_DRAIN_MS` (25 s), then exits; the job's lease returns it. Railway's draining time for the worker must be ≥ `WORKER_DRAIN_MS` (owner check).
4. **Jobs the older worker does not handle**: the old worker fails unknown job types (`finishJob` with retry/backoff, then `failed`). Find them with a dry-run `SELECT type, status, count(*) FROM jobs WHERE updated_at > <rollback time> GROUP BY 1,2` (owner session). After rolling forward, requeue through the tested path only. `enqueueJob(type, payload, { tenantId, dedupeKey: <original>, requeueCompleted: true })` (rules in `jobs.integration.test.ts`: rearms `done`/`failed`, never resets a running lease) accepts only the job types in its allowlist in `src/lib/jobs/queue.ts`; any other type (for example `billing.reconcile`, `usage.housekeeping`, `workspace.export`, `workspace.export_sweep`, `payments.reconcile_sweep`) throws `Invalid job contract`. For those, run the same `INSERT ... ON CONFLICT (dedupe_key) DO UPDATE` statement `enqueueJob` issues with `requeueCompleted=true` (it touches only `done`/`failed` rows whose type and tenant_id match, and resets attempts and run_at), as the worker role, with the job's original type, tenant_id, payload and dedupe_key. There is no operator UI or script for this today: it needs a trusted one-off `tsx` or `psql` session with the worker credentials. Never a hand-written `UPDATE jobs SET attempts=0`, which ignores the type/tenant match and can reset a running lease.
   **A failed migration (P3009)**: if `prisma migrate deploy` aborts (for example on the 5 s `lock_timeout` of a policy migration such as `20261113090200_ops_health_outbound_intents_policy`), later deploys refuse to run until it is resolved. The migration's transaction rolled back, so nothing is half-applied: run `npx prisma migrate resolve --rolled-back <migration_name>` with `MIGRATION_DATABASE_URL`, then re-dispatch the "Apply production Prisma migrations" workflow at a quieter time. For a `CREATE INDEX CONCURRENTLY` migration, first drop the INVALID index it left (`DROP INDEX CONCURRENTLY <name>`, named in the migration's comment).
5. **Verify**: `/api/health` 200, deep check `migrations.latest` unchanged, `worker.ok`, queue draining, platform console Health page. Rolling back to a release before Phase 15 removes the deep check (that code answers `?deep=1` with the plain `{"status":"ok"}`) and the worker heartbeat: verify the worker from Railway logs (`[worker] ready`, no `[worker] job failed` storm) and the platform console Job backlog instead. Monitor B alerts on a body without `"checks"`, so it reports the lost deep mode (alerts.md).
6. **Local rehearsal** (owner-pending until run): migrate the local Docker DB to HEAD (`node scripts/test-db-local.cjs setup`), `git worktree add ../rollback <commit SHA of the currently deployed Railway release>` (Railway → service → Deployments → the active deployment's details; for the Phase 15 merge that is the Phase 14 commit `3d7926f`; the repository has no release tags), install there, run its `jobs.integration.test.ts` and `postgres.integration.test.ts` with the env built like `test-db-local.cjs#isolatedEnv`. Record the result in the release checklist.
