# Bodhinox Chat functionality and acceptance

This application is adapted from WACRM 0.8.0. The complete upstream file/route/table inventory is in [the repository review](2026-10-14-wacrm-repository-review.md). This document describes the migrated foundation, not a claim that every external provider has passed production acceptance.

| Area | Available implementation | Acceptance boundary |
| --- | --- | --- |
| Dashboard | Conversation/contact/deal/message analytics, activity and charts. Messages per day, response time by weekday and open deal totals come from `GET /api/dashboard/charts` (7/30/90 days), grouped in SQL inside withTenant on the workspace timezone's days, so no 1,000-row page cap applies | Local browser renders against isolated Railway PostgreSQL |
| Identity | Password login, short-lived RS256 JWT, rotated refresh cookies, CSRF, revocation, TOTP and recovery codes | Unit and real database tests; MFA is optional for every role (enrolled users must pass it at sign-in; the platform console still requires it) |
| Email onboarding | Verification, reset, invitations and verified email change. Signing up again with an already-verified email sends a "you already have an account" sign-in notice (same on-screen response, so registered emails are not revealed); a still-unverified signup gets a fresh verification link. The link alone does not verify: it opens /verify-email, which asks for the password chosen at that sign-up, and that password (with that sign-up's name and terms) becomes the account's, so whoever signed up first with someone else's address never keeps the account (audit #55); verifying ends every other pending link, removes the password hashes those links carried, and clears sessions, MFA factors and Google links left on the unverified row. Signing up from an invitation link creates no personal owner workspace: an email signup carries the invitation (hash only) on its verification and joins the inviting workspace with the invited role when the email is verified (a Google signup joins at once), marking the invitation used and auditing `invitation.redeemed`. A used, expired, unknown or malformed link is refused before the email is looked at (410 `invite_unavailable` / `google_invite_unavailable`, the same for registered and new emails) with nothing created; an already-registered address is mailed the join link. If the link is used up before an invited signup verifies, or a member loses their last membership, the next sign-in creates a personal workspace instead of refusing. Sign-in without a chosen workspace returns to the workspace the latest session ended in (tenant switches move it) while the person is still a member, otherwise the oldest membership | Provider deliberately deferred; mail-dependent operations fail closed until SMTP configured |
| Accounts | Owner/admin/agent/viewer, invitations (new users join the inviting workspace directly; existing users accept on /join), membership switching (remembered for the next sign-in), transfer. Account emails (verify, password reset, already-registered notice with the invite link, email change, delivery test) and the notification digest are written in the build locale (AuthEmails messages), English when unset | Scoped repository and identity tests; additional SaaS billing/provisioning is future work |
| Contacts | Create/edit, phone deduplication, CSV, tags, notes, custom values. CSV import reads common header names (Mobile, Phone Number, WhatsApp, Name, First/Last Name, Email Address, Organisation, Labels), quoted line breaks, semicolon files and a byte-order mark, keeps apostrophes, and takes an optional country code for numbers written without + (one leading trunk 0 is dropped; a number already starting with that code and 10+ digits after it is kept). Rows go to `POST /api/contacts/import` in batches of 200 (agent+): new numbers are inserted with ON CONFLICT on the workspace number index, existing ones are skipped or, when chosen, updated (blank cells keep stored values) and tagged; rejected rows are listed with a reason and can be downloaded as a CSV. Our own export's Opted out at and Blocked at columns are read back: a new contact keeps the opt-out (source import) and block, an existing one gets them only when updating was chosen, and an import never clears an opt-out or a block. The import has three steps (choose file, match columns, done): each column is matched to a contact field (phone, name, first/last name, email, company, city, tags, opted out at, blocked at), a custom field or nothing, guessed from the header and changeable, with a sample value and checks for a missing phone column or a field chosen twice; a label can be added to everyone imported, and custom values that do not fit their field's type are skipped and counted. Import and bulk tagging do not run tag_added automations. Bulk actions (add to / remove from list, add tag, remove tag, assign owner, pause automations, set field, unsubscribe Instagram, export the ticked rows, delete) work on the ticked rows or on every contact matching the current view (`POST /api/contacts/bulk`, agent+, at most 50,000, refused with 409 when the match count is no longer the one shown). The table (Contacts > People) lists through `GET /api/contacts/bulk/view` 25 per page with columns Name (email or city below), Channels (number, Instagram username, Opted out / Blocked / Instagram status), Labels, Owner, City and Last active (latest message of the conversations the member may see); headers and a Sort menu sort by name, city, owner, last active or date added; filters are segment, list, labels, owner (including No one), channel, consent and subscribed only. A row opens the full-page profile | Real database tests (`src/lib/contacts/import-bulk.integration.test.ts`: workspaces over 1,000 contacts, updates, tenancy, viewer refusal, count check) and local browser create/edit smoke; the import runs in the open tab (a closed tab stops it; re-importing the same file is safe) |
| Segments and export | Saved segments: named filters (tags has any/none, custom field is/is not/contains/empty, name/phone/email/company contains or empty, created before/after, opted out, blocked; all conditions must match) with a live matching/marketable count, a contacts-page view and use as a campaign audience. Contacts > Segments shows each segment as a card (`GET /api/segments/overview`: live count, up to four member faces, conditions in plain words, a warning when a tag, list, field or campaign it uses was deleted) with View people, Use in campaign (opens a new broadcast with the segment chosen) and Edit, Duplicate, Export people and Delete. Admin-only CSV export of all contacts or one segment (tags, consent, custom fields), formula-safe and audit-logged | Unit, real database (every operator, tenancy, roles, export, segment campaigns) and browser tests; export is capped at 50,000 contacts and built in memory |
| Lists, tag categories and workspace attributes | Static lists: hand-picked contacts (bulk Add to list / Remove from list on the contacts page), viewable and exportable like segments, usable as a segment condition (in any / none of) and as a "Static list" campaign audience with an exact consent-aware count. Tags carry an optional category; settings and the contacts tag filter group by it. Workspace attributes (Settings → Fields & tags, admin-only) fill `{{workspace.key}}` in flow and automation text; secret attributes are stored encrypted, never returned to the browser and only resolved in automation webhook bodies and headers | Unit, real database (membership, tenancy, viewer refusal, list campaigns and export, secret storage) and browser tests; lists cannot be renamed yet and changes are limited to 1,000 contacts per request |
| Plans and entitlements | A plan catalogue (free, basic, pro, enterprise) of feature switches and numeric limits, an account subscription, and one server-side check used by the API handlers: scheduled campaigns, contact export, API campaigns, click tracking, retargeting and workspace attributes are features; seats (members plus open invitations), saved segments, lists, recipients per campaign, active flows and active automations are limits. Settings → Plan & usage shows the plan and usage; gated controls show an Upgrade badge A time-based automation with a send step (send template, message, buttons or list) is a recurring scheduled campaign: saving or activating it needs the scheduled-campaigns feature (402), and every occurrence re-checks that feature and the recipients-per-campaign limit; if the plan now refuses, the automation is turned off with a failed log entry saying why instead of retrying. Reconnecting a number an admin removed takes a WhatsApp-numbers slot again (402 when full), checked under the same lock and transaction as the write. | Real database tests that a smaller plan refuses every gated action through the server API and leaves nothing behind. A workspace without a subscription is unrestricted (enterprise); a cancelled subscription falls back to free. Payments and self-serve plan changes are not built yet |
| Consent | Opt-out (STOP/UNSUBSCRIBE; START/SUBSCRIBE opts back in) and block, toggled from the contact panel. Opted-out contacts get no broadcasts, scheduled automations or template steps; blocked contacts get no automated messages, flows or AI replies. Enforced when audiences are built and again at send time STOP also ends the contact's running flows, and a flow's send-template step re-reads consent before each send, so a timer or payment resume never sends a template to an opted-out or blocked contact. | Unit, real database and browser tests; keywords are fixed English words, and no confirmation reply is sent |
| WhatsApp opt-in record | Each contact's WhatsApp consent shows as Opted in / Opted out / No opt-in with its date and source (customer replied START or STOP, a teammate, the API, an import): a chip in the chat header, a Consent section in the inbox contact panel (agents record an opt-in after a confirmation step, or opt out), a banner above the composer when opted out, a mark on list rows and a Consent filter in **+ Filter**. Right: Labels, Messaging (one switch per channel: WhatsApp opt-out/opt-in and Instagram subscription through `POST /api/contacts/[id]/consent`, "Not connected" when the contact has no number or Instagram identity) with Instagram identities, Conversations (the ones the member may see), Orders (agent+) and Deals. | Campaigns | Approved templates, all/tag/custom-field/CSV/segment/list audiences, exclusions, personalized frozen parameters (resolved in SQL), background delivery and retry. Retargeting: a segment condition selects contacts by their outcome in an earlier campaign (received, delivered, read, replied, failed, received but not read, not received). CSV audiences can map any CSV column into a template variable and optionally send once per row for repeated numbers. Test send to up to 3 numbers before launch (refuses opted-out/blocked numbers; unmatched values show as [name]; not recorded on any campaign). The campaign list has status tabs, name search and pagination. Click tracking: a template whose URL button is <APP_URL>/r/{{1}} gets a per-recipient token; /r/<token> records the click (keyed IP hash) and 302s only to the campaign's stored https destination, and the campaign page shows unique clickers. API campaigns are created in the dashboard with a template and filled through POST /api/v1/broadcasts/{id}/recipients (1,000 per batch, broadcasts:send). The campaign list shows the number's quality rating, daily tier and an estimate of what is left today (campaign sends only). Send now or schedule up to 90 days ahead; a scheduled campaign can be rescheduled or cancelled until its job starts, and a cancelled one never sends. Meta rate-limit rejections (codes 4, 80007, 130429, 131056) pause the pass and retry the same recipient with 1–30 minute backoff; other rejections are final and uncertain outcomes are never resent: they are left out of "Retry failed" and listed on the campaign page, where an admin marks each as sent or not sent after checking (audited; not sent makes it an ordinary failure for the next retry). "Retry failed" sends a recipient Meta accepted and a status webhook later failed once more under a new retry generation, and the Resume/Retry confirmation shows the real recipient count. "Sync from Meta" times out each Meta page after 15 s with a clear message, writing nothing. The legacy `POST /api/whatsapp/broadcast` bulk-send endpoint is removed (it had no recipient cap, plan or suspension checks); every send goes through `/api/broadcasts/create` and the schedule/resume routes, and the browser data API may only save an inert draft or rename a campaign. A reply marks the contact's latest open campaign send as replied only when it came in on the same number and within 72 hours. Campaigns redesign: Broadcasts, Templates (now at /templates; Settings > Templates still works), Ads and Forms share one "Campaigns" header whose button follows the tab. The campaign list shows each row's audience, sent, delivered, read and replied figures, a sent-progress bar, a channel dot and a row menu (open, edit or reschedule, send now, cancel schedule, pause, resume, retry failed, duplicate, delete), with Draft/Scheduled/Sending/Sent/Paused/Failed/Cancelled tabs and counts. Pause (POST /api/broadcasts/[id]/pause, campaigns.send, audited) stops a sending campaign between recipients and leaves the rest pending; Resume continues it. Send now moves a scheduled campaign's single queued job to now. Duplicate (and a draft's Edit) reopens the wizard prefilled. The wizard starts with name and channel. Instagram broadcasts (POST /api/broadcasts/instagram) send a free-text message, with {first name}, only to contacts whose 24-hour Instagram window is open now (no CSV audience, no scheduling); each recipient is frozen with its Instagram conversation, the window, consent and account are re-checked before every send, and each send goes through its outbound intent (an ambiguous outcome is flagged for reconciliation). The campaign report adds a Message card (the template or text as a chat bubble with the campaign's values), recipient status chips with counts, a name/number search and paging. Template cards show the chat preview, a category filter and a Use button that opens the wizard with the template. The Ads tab opens a read-only drawer per campaign or ad with KPI tiles and a 14-day chart (spend, clicks or conversations). Forms list search and a published count, and search on responses. | Atomic campaign/recipient/job and rollback tests, a 2,500-recipient real database test, start-versus-cancel race, reschedule refusal once started, throttle unit tests and a browser schedule/cancel test; up to 50,000 recipients (10,000 CSV rows); recipients and parameters are frozen when the campaign is created, consent is rechecked at send; fixed pacing of about 6 sends per second |
