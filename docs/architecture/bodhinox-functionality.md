# Bodhinox Chat functionality and acceptance

This application is adapted from WACRM 0.8.0. The complete upstream file/route/table inventory is in [the repository review](2026-10-14-wacrm-repository-review.md). This document describes the migrated foundation, not a claim that every external provider has passed production acceptance.

| Area | Available implementation | Acceptance boundary |
| --- | --- | --- |
| Dashboard | Conversation/contact/deal/message analytics, activity and charts | Local browser renders against isolated Railway PostgreSQL |
| Identity | Password login, short-lived RS256 JWT, rotated refresh cookies, CSRF, revocation, TOTP and recovery codes | Unit and real database tests; production owner/admin requires MFA |
| Email onboarding | Verification, reset, invitations and verified email change | Provider deliberately deferred; mail-dependent operations fail closed until SMTP configured |
| Accounts | Owner/admin/agent/viewer, invitations, membership switching, transfer | Scoped repository and identity tests; additional SaaS billing/provisioning is future work |
| Contacts | Create/edit, phone deduplication, CSV, tags, notes, custom values | Real database tests and local browser create/edit smoke |
| Segments and export | Saved segments: named filters (tags has any/none, custom field is/is not/contains/empty, name/phone/email/company contains or empty, created before/after, opted out, blocked; all conditions must match) with a live matching/marketable count, a contacts-page view and use as a campaign audience. Admin-only CSV export of all contacts or one segment (tags, consent, custom fields), formula-safe and audit-logged | Unit, real database (every operator, tenancy, roles, export, segment campaigns) and browser tests; export is capped at 50,000 contacts and built in memory |
| Lists, tag categories and workspace attributes | Static lists: hand-picked contacts (bulk Add to list / Remove from list on the contacts page), viewable and exportable like segments, usable as a segment condition (in any / none of) and as a "Static list" campaign audience with an exact consent-aware count. Tags carry an optional category; settings and the contacts tag filter group by it. Workspace attributes (Settings → Fields & tags, admin-only) fill `{{workspace.key}}` in flow and automation text; secret attributes are stored encrypted, never returned to the browser and only resolved in automation webhook bodies and headers | Unit, real database (membership, tenancy, viewer refusal, list campaigns and export, secret storage) and browser tests; lists cannot be renamed yet and changes are limited to 1,000 contacts per request |
| Plans and entitlements | A plan catalogue (free, basic, pro, enterprise) of feature switches and numeric limits, an account subscription, and one server-side check used by the API handlers: scheduled campaigns, contact export, API campaigns, click tracking, retargeting and workspace attributes are features; seats (members plus open invitations), saved segments, lists, recipients per campaign, active flows and active automations are limits. Settings → Plan & usage shows the plan and usage; gated controls show an Upgrade badge | Real database tests that a smaller plan refuses every gated action through the server API and leaves nothing behind. A workspace without a subscription is unrestricted (enterprise); a cancelled subscription falls back to free. Payments and self-serve plan changes are not built yet |
| Consent | Opt-out (STOP/UNSUBSCRIBE; START/SUBSCRIBE opts back in) and block, toggled from the contact panel. Opted-out contacts get no broadcasts, scheduled automations or template steps; blocked contacts get no automated messages, flows or AI replies. Enforced when audiences are built and again at send time | Unit, real database and browser tests; keywords are fixed English words, and no confirmation reply is sent |
| Inbox | Assignment, status, unread reset, text/media/template/interactive composition, reactions and quotes | Scoped read/write tests; actual WhatsApp transport requires Meta credentials |
| Human handoff | Persistent bot pause before manual sending; explicit resume | Role/database checks and flow/automation guards; viewer cannot mutate |
| Pipelines | Stages, deal boards, values and contact relationships | Migrated tenant-scoped CRM operations; business-specific sales workflows remain configurable |
| Campaigns | Approved templates, all/tag/custom-field/CSV/segment/list audiences, exclusions, personalized frozen parameters (resolved in SQL), background delivery and retry. Retargeting: a segment condition selects contacts by their outcome in an earlier campaign (received, delivered, read, replied, failed, received but not read, not received). CSV audiences can map any CSV column into a template variable and optionally send once per row for repeated numbers. Test send to up to 3 numbers before launch (refuses opted-out/blocked numbers; unmatched values show as [name]; not recorded on any campaign). The campaign list has status tabs, name search and pagination. Click tracking: a template whose URL button is <APP_URL>/r/{{1}} gets a per-recipient token; /r/<token> records the click (keyed IP hash) and 302s only to the campaign's stored https destination, and the campaign page shows unique clickers. API campaigns are created in the dashboard with a template and filled through POST /api/v1/broadcasts/{id}/recipients (1,000 per batch, broadcasts:send). The campaign list shows the number's quality rating, daily tier and an estimate of what is left today (campaign sends only). Send now or schedule up to 90 days ahead; a scheduled campaign can be rescheduled or cancelled until its job starts, and a cancelled one never sends. Meta rate-limit rejections (codes 4, 80007, 130429, 131056) pause the pass and retry the same recipient with 1–30 minute backoff; other rejections are final and uncertain outcomes are never resent | Atomic campaign/recipient/job and rollback tests, a 2,500-recipient real database test, start-versus-cancel race, reschedule refusal once started, throttle unit tests and a browser schedule/cancel test; up to 50,000 recipients (10,000 CSV rows); recipients and parameters are frozen when the campaign is created, consent is rechecked at send; fixed pacing of about 6 sends per second |
| Templates | Settings → Message templates: standard, carousel (2–10 image or video cards with the same button layout), authentication (one-time code with copy button, optional security note and 1–90 minute expiry) and limited-time offer (offer text, optional expiry, copy-code then URL button) templates, plus a location header; field-level checks for Meta's limits, including no variable at the start or end of a body and no leftover library placeholder links or numbers. Save as draft locally and submit later; status filter tabs, quality chip, duplicate, and a status history (draft, submit, Meta webhook, sync and edit events, recorded only on change). A library of 28 ready-written Utility and Marketing templates and an AI writer (uses the workspace AI provider, validated before it is shown, never submitted automatically) prefill the editor. Inbox and campaigns collect location, offer expiry, coupon and per-card values; authentication templates send only from the inbox or API; automations accept only templates whose values are all in the body | Unit tests for every kind's validators, Meta submit and send payloads, drafts, history, duplicate, sync and submit races; real database tests for the history table and its tenancy; a browser test for library → draft → duplicate → history. Meta approval of the new kinds still needs a live account; a location header is not drawn in the inbox bubble |
| WhatsApp Forms | Forms (Meta Flows) built in the app: up to 10 screens of headings, text, short and long answers, email, phone, number, date, dropdown, radio, checkboxes and opt-in, each answer optionally saved to the contact's name, email, company or a custom field; a live WhatsApp-style preview; publish to Meta (one Meta flow per form, its validation errors shown on the form; published forms are read-only and can be duplicated). Send from the inbox, a Send form flow step (the run waits for the answers, which become variables, with a timeout path) or a FLOW button on a template, including campaigns (one session per recipient). Answers are stored once per inbound message and listed per form, with an admin CSV export. Forms that check answers on the server use an encrypted endpoint (RSA-OAEP/AES-GCM, signed requests, per-send tokens) and a key generated in Settings → WhatsApp; rotation is serialized and a pending key keeps forms working if the save fails | Unit tests for definitions, Flow JSON, crypto, endpoint actions, routes and sends; real database tests for tenancy, sessions, responses, publish and key rotation; browser tests for creating and saving a form. Publishing and sending need a live Meta account; the inbox shows a sent form as text, not a card |
| WhatsApp numbers | A workspace can connect several WhatsApp numbers (any WABA): one is the default; each conversation belongs to one number and every reply, flow step, automation, AI reply, form and campaign sends from its number (templates must be in that number's WABA). Connect with Facebook (Embedded Signup; needs NEXT_PUBLIC_META_APP_ID and NEXT_PUBLIC_META_EMBEDDED_SIGNUP_CONFIG_ID at build, accepts an existing two-step PIN) or manually; edit the business profile; ice breakers and forms keys per number; inbox, campaign, flow and form number pickers when 2+ numbers. Health (quality, tier, name status) syncs every 6 hours with one admin alert per change; a green-tick checklist links to Meta. Disconnecting keeps the number's record: its threads keep their number, sends from it are refused (never re-routed), active flows bound to it go to draft and its campaigns are held until it is reconnected; another workspace may connect it once it is disconnected | Unit and real database tests for routing, sends per number, disconnect and reconnect, number moves between workspaces, signup and health; Embedded Signup needs Meta Tech Provider approval and was not exercised against Meta |
| Commerce | Connect a Meta catalogue to a number (cart and visibility settings) and sync its products every 6 hours; send a product, a product list (up to 30 in 10 sections) or the catalogue from the inbox or a flow. WhatsApp cart orders become orders (items, quantities, prices in minor units) with an Orders page, status changes, an optional confirmation reply and an order_received flow trigger. Razorpay payment links (keys stored encrypted; test/live from the key) from the inbox, an order or a flow step that waits for paid / expired / failed; a timed-out create is held as unknown and reconciled, never duplicated, and a link is only marked paid from a verified webhook or fetch. Shopify app (OAuth, order/fulfilment/checkout webhooks, GDPR redaction that erases contacts created from store data) and WooCommerce webhooks feed event rules that send an approved template after a delay, respecting consent and skipping abandoned checkouts that became orders; ambiguous sends appear under Needs attention for an admin to resolve. Outbound webhooks gain order.created, order.paid and payment_link.paid; docs/integrations/zapier-and-google-sheets.md has recipes | Unit and real database tests for money, catalogue sync, order parsing, payment links and webhooks, Shopify and WooCommerce signatures, rules and redaction; none of it was exercised against live Meta, Razorpay, Shopify or WooCommerce accounts |
| Inbox premium | Internal notes per conversation with @mentions (visible to every member, never sent to WhatsApp; authors edit, authors or admins delete; open notes panels refresh live from conversation_notes events that carry ids only). Conversation lifecycle (bot / requesting / assigned / resolved) and a first-reply SLA kept by database triggers; the inbox resolves and reopens by writing status, and the lifecycle, SLA and reopen columns are read-only to the browser. Routing rules with round-robin and reassign-after-minutes, working hours with an away message, auto-resolve after idle hours, SLA-breach alerts. Message full-text search, saved inbox filters, quick-reply favourites and a media library. Per-member phone masking (admins set it for agents and viewers): numbers are masked server-side in CRM reads, realtime events, audience pages, search and in numbers quoted in notification titles/bodies and digest emails. Notifications for assigned-conversation messages, mentions, SLA breaches, finished campaigns, rejected templates and number health, each with an icon and translated label; a click follows the notification's server-chosen relative link only. Per-member notification preferences and a 30-minute email digest (titles and links only) when SMTP is configured. Viewers can preview and page saved segments (segment reads take no row lock) | Unit and real database tests for notes, lifecycle, routing, SLA, search, saved filters, media library, masking (including notification text), notification links, browser-write contracts for lifecycle and notification columns, note realtime projection and viewer segment paging; e2e/inbox-premium.spec.ts covers notes (including a live note), mention notification click-through, search, working hours and saved views |
| Billing and plans | Self-serve subscriptions on the platform's Razorpay account (Settings → Plan & usage → Billing): plan picker with Razorpay Checkout, GST billing profile and tax invoices (CGST+SGST or IGST, gapless numbering per financial year), upgrades now (prorated) and downgrades or cancellation at the end of the paid period, past_due → 7-day grace → suspended (automatic sends paused) → recovery on payment, add-on packs (AI messages, seats, WhatsApp numbers) and usage meters. Every provider call is recorded before it is made (billing_intents, add_ons 'pending') and an ambiguous outcome is reconciled from the provider's state, never retried or assumed; the plan and paid state change only from the provider's reported state (verified webhook, then a fetch, or the sweep). A checkout authorised after it was replaced, or a second subscription beside a live one, is cancelled at the provider, audit-logged and admins are notified instead of switching the workspace. When a plan switch takes effect (scheduled downgrade at renewal, cancellation to Free, upgrade, recovery) segments, lists, active flows and active automations beyond the new limits are archived, never deleted, keeping the admin's saved choice (Choose what stays dialog) or else the most recently used, and restored when the limits allow again. Billing mutations need an admin with the 'settings.billing' permission, a live session and Origin/CSRF proof. Workspaces without a subscription stay unrestricted. Google sign-in, teams and per-feature permission restrictions ship in the same phase | Unit tests for the state machine, plan-switch rule, Razorpay client and webhook parsing (including payment.failed), GST, invoice numbering, add-ons and every billing route (role, permission, CSRF); real database tests for checkout, webhooks, grace/suspension, plan changes, cancel reconciliation, superseded-checkout cancellation, payment.failed and non-destructive downgrade archiving with restore |
| Automation | Event/keyword/tag/status triggers, conditions, delays, replies, CRM actions, scheduled audiences and round-robin assignment over owner/admin/agent members | Engine tests, durable jobs, scoped scheduler checks and a concurrent round-robin database test; actual provider sends still require acceptance |
| Visual flows | Node editor, input validation, branching, buttons/lists, CRM actions, media, fallbacks, timeout and handoff logs. Ask question takes any text, a number (with min/max), a date, yes/no, email, phone or a pattern, with optional attempts, an error message, an "attempts used up" path and a Skip button. Ask for media / location / address store the file link, coordinates or address fields as variables (the address form is WhatsApp's own, for Indian numbers; others type it). Set attribute writes a variable, contact field or custom field. Conditions combine up to 10 rules (all / any) including numbers, dates, time-of-day windows and today's date in a chosen timezone. Any step can wait up to 24 hours before it runs, and a step waiting for a reply can time out to its own path; both are durable jobs that survive restarts. Send template sends an approved template (also outside the 24-hour window) and routes on each quick-reply tap. API request calls an external API (method, URL, query, headers, JSON body filled from variables, contact fields and workspace attributes, with secrets allowed only in headers and the body), stores dot-path values from the JSON reply and routes on up to 5 status codes or classes plus a fallback; the editor can test a request first. Requests refuse private and local addresses (checked again when connecting), never follow redirects, time out after 10 seconds and cap replies at 256 KB. Assign agent assigns the chat (a member or the next in the round robin) and carries on; Connect flow ends the run and starts another active flow for the same contact with the same variables, stopping after 5 connects in a row without a customer reply. A non-admin cannot add or change an API request step that uses a secret workspace value, and only an admin's test request sends secrets. Triggers: keywords (chips, exact or contains, case option), a regex, a tap on a sent template's quick-reply button (the button text is saved as `trigger_button`; broadcast taps are matched through the reply's context id), the first message, or an ice breaker (up to 4 prompts set in Settings → WhatsApp and sent to Meta; a tap arrives as its text and matches an exact keyword). Order when several match: an active run first, then template reply, then keyword or regex, then first message; automations and the AI reply only get what no flow took. A draft with test numbers (up to 3) runs only for those numbers, wins over a live flow with the same trigger for them, must pass activation checks and counts toward the plan's active flows; activating it makes it live and clears its test numbers. A default fallback message (text, or an image or video with caption) is sent with every off-script reply before the reprompt, handoff or end. New flows can start from a gallery of 26 Bodhinox-written templates in 11 industries (search and category filter; every template passes activation checks in every language). The flows list has search, a status filter, a Created by name and Duplicate (a draft copy with its steps and positions; a non-admin cannot copy a flow whose API step uses a secret). The canvas can be locked (no moving, connecting, deleting or editing), a selected or hovered connection shows a delete button, and dropping a connection on empty canvas opens a step picker that adds and wires the step. Preview walks the unsaved flow as a WhatsApp-style chat: it checks typed answers like the engine, follows buttons, lists and condition branches, can simulate a timeout or used-up attempts, and never sends anything | Unit, real database (timer redelivery, stored locations) tests; a reply during a delay is recorded but ignored, a delay or timeout that crosses WhatsApp's 24-hour window fails that send (no template fallback yet), and Ask for address shows the native form only to Indian numbers |
| AI | Drafts, automatic replies, provider settings, knowledge documents, embeddings, playground and usage | Source/engine tests; configure and accept the chosen AI provider separately |
| Private media | Tenant object authorization, S3 storage, authenticated reads, bounded uploads and expiring provider URLs | Local policy/route checks; Railway bucket provisioned; live storage acceptance tracked in deployment runbook |
| Live updates | Authenticated SSE, scoped outbox, cursor replay, deduplication and reconnect | Database replay tests, including equal-timestamp batches |
| Integrations | Official Meta Cloud API, API keys, outbound signed webhooks (message, conversation, broadcast, template and flow events; managed in Settings → API & webhooks or the API) and MCP client | Webhook tenancy/role tests; Meta, AI and outbound destinations require their own acceptance; Wasender is not integrated |

Supabase Auth, Storage, Realtime, client and database dependencies have been replaced. Prisma owns migrations; constrained PostgreSQL roles and FORCE RLS protect tenant data. A dedicated worker owns durable background execution. Browser writes use fixed resources and dedicated validated actions; SQL, roles and provider credentials are never accepted from the browser.

The worker uses leases and persisted outbound intents. Interrupted actions with unknown external outcomes require reconciliation before retrying. This deliberately does not promise exactly-once external delivery. Keep one web and one worker replica until shared rate limiting and provider throughput coordination are implemented.

See [database evidence](database-validation.md), [authentication evidence](authentication-validation.md), [data-access evidence](data-access-validation.md), and [deployment and remaining configuration](../deployment/railway.md). The isolated preview account contains synthetic data and does not represent production onboarding.
