## Releases

1. Run local/CI typechecking, linting, unit and isolated PostgreSQL integration tests and the production build.
2. Review additive migrations. Existing applied migration files are immutable.
3. Take a Railway backup before changing a database that contains customer data. The initial target was verified empty.
4. Push to `main`. The "Bodhinox validation" workflow runs every check and, only if they pass, its `migrate` job applies pending migrations to production through the reusable "Apply production Prisma migrations" workflow and the `MIGRATION_DATABASE_URL` secret in the GitHub `production` environment. The web and worker services never hold the owner credential. The workflow can still be dispatched by hand, or `npm run db:migrate` run locally with the migration-owner URL. Role bootstrap is only required for onboarding or coordinated role-password rotation.
5. Railway deploys both services only after those GitHub checks succeed: **Wait for CI** (`checkSuites`) must stay enabled in each service's source settings, otherwise code can go live before its migration (as on 1 November 2026, when contacts and the inbox returned 500 for about six minutes). Wait for SUCCESS and verify /api/health, unauthenticated login, protected page redirects and worker readiness.
6. Configure SMTP and Meta credentials when ready, then test signup/verification/MFA, inbound status and message webhooks, private media, a single approved recipient send, and broadcast completion with the browser closed.

Keep one web and one worker replica until shared API rate limiting and provider-wide throughput coordination have been implemented and measured. PostgreSQL job claims and lease fencing support crash recovery; browser request rate-limit buckets are currently process-local. Avoid overlapping worker releases; uncertain dispatches require operator reconciliation.

Migration `20261101000000_round_robin_cursor` adds the worker-only `assignment_cursors` table used by round-robin assignment. It is additive and needs no backfill; run it with the normal migration step before deploying the code that uses it.

Migration `20261101010000_contact_consent` adds nullable `opted_out_at`, `opt_out_source` and `blocked_at` columns to `contacts`. It is additive, needs no backfill (existing contacts start as not opted out and not blocked) and must run before the code that reads the columns.

Migration `20261101020000_segments` adds the tenant-scoped `segments` table (RLS: members read, agents and above write). It is additive and is applied automatically by the CI `migrate` job before Railway deploys the code.

Migration `20261101030000_lists_attributes_tag_categories` adds nullable `tags.category`, the `contact_lists` and `contact_list_members` tables (members read, agents and above write) and `workspace_attributes` (members and the worker read, admins write). It is additive with no backfill. Secret workspace attributes are encrypted with the existing `ENCRYPTION_KEY`; rotating that key makes stored secrets unreadable, so re-enter them after a rotation.

Migration `20261102000000_broadcast_cancelled_status` widens the `broadcasts.status` check to allow `cancelled`. Scheduled campaigns need no extra process: their dispatch job waits in `jobs` with `run_at` set to the scheduled time, so the existing single worker starts them. A campaign that stays throttled by Meta for about an hour pauses with its remaining recipients pending; resume it from the campaign page.

Migration `20261102010000_campaign_tracking_api` adds `broadcasts.kind`, `tracked_url` and `click_count`, `broadcast_recipients.click_token` and `clicked_at`, the `broadcast_clicks` table and the SECURITY DEFINER `resolve_click_token(text)` (worker only). Additive with no backfill. Click tracking needs templates whose URL button is exactly `<APP_URL>/r/{{1}}`, so `APP_URL` must stay the public app origin; changing it breaks tracking for templates created with the old origin.

Migration `20261102030000_entitlements` adds the `plans` catalogue (seeded with free, basic, pro and enterprise) and `account_subscriptions`. Existing workspaces have no subscription row and stay unrestricted. Until billing exists, an operator assigns a plan with the migration owner, for example `INSERT INTO account_subscriptions(account_id, plan_id) VALUES ('<account uuid>', 'pro') ON CONFLICT (account_id) DO UPDATE SET plan_id = EXCLUDED.plan_id, status = 'active'`. Lowering a plan never deletes data: existing segments, lists and active flows stay, but new ones beyond the limit are refused.

Migration `20261102040000_flow_builder_nodes` widens the flow node and run-event CHECK lists and adds `flow_runs.delay_until`; it changes no existing rows. Flow delays and reply timeouts are `flow.timer` jobs run by the worker, so the worker must be deployed with the web service: a timer queued before the worker restarts runs when it comes back (late, never twice). Inbound locations and WhatsApp address-form replies are now stored in `messages.interactive_payload`.

Migration `20261102050000_flow_integration_nodes` widens the same CHECK lists for the template, API request, assign agent and connect flow steps; it changes no existing rows. Flow nodes are now read-only through the generic browser data API (the flow editor saves through `PUT /api/flows/[id]`). API request steps call customer-configured URLs from the worker; outbound traffic must be allowed from the worker service.

Migration `20261102060000_flow_triggers_testing` adds the `template_reply` flow trigger, `flows.test_numbers` (at most 3, digits only) and `whatsapp_config.ice_breakers` / `ice_breakers_synced_at`; it changes no existing rows. Inbound-action jobs may now carry `contextMetaId`; jobs queued before the deploy are still accepted without it. Ice breakers are saved only after Meta's conversational_automation endpoint accepts them.

Migration `20261102070000_template_studio` adds `message_templates.template_kind` (default `standard`), `cards`, `auth_options`, `lto`, the `location` header type and the append-only `template_status_events` table (FORCE RLS; members read, admins and the worker insert). Existing templates keep working unchanged as standard templates. The data layer now binds a JavaScript null as SQL NULL for JSON columns (before, it stored the JSON value null). The template AI writer uses the workspace's configured AI provider and answers 409 when none is set.

Migrations `20261102080000_whatsapp_forms`, `20261102080500_whatsapp_form_session_answers` and `20261102081000_whatsapp_forms_pending_key` add `whatsapp_forms`, `whatsapp_form_sessions` and `whatsapp_form_responses` (FORCE RLS), the `send_form` flow step and form events, and the forms key columns on `whatsapp_config` (the private keys are encrypted and never in a browser resource). Forms that check answers on the server call `APP_URL/api/whatsapp/forms/endpoint/<accountId>`: it must be reachable over HTTPS and `META_APP_SECRET` must be set (requests without a valid signature are refused). An admin generates the encryption key in Settings → WhatsApp before publishing such a form; a rotation holds a 120-second lease.

Migrations `20261102090000_whatsapp_multi_number` through `20261102103000_whatsapp_verify_connected_only` make WhatsApp numbers per workspace plural: every existing number becomes its workspace's default and existing conversations, campaigns and templates are stamped with it (a backfill with triggers paused; it takes short table locks). Conversations become unique per (contact, number); one active flow run is allowed per conversation; phone_number_id is unique only among connected numbers; the webhook verify token of a disconnected number no longer verifies. Set NEXT_PUBLIC_META_APP_ID and NEXT_PUBLIC_META_EMBEDDED_SIGNUP_CONFIG_ID as build variables to show Connect with Facebook. The worker runs a whatsapp.health_sync job every 6 hours per connected number.

Migrations `20261102110000_commerce` through `20261102115000_commerce_event_reconciliation` add catalogues, products, orders, payment providers and links, commerce event rules and events, Shopify and WooCommerce stores (all FORCE RLS; secrets encrypted and never in a browser resource). Razorpay: an admin saves the key id, key secret and webhook secret in Settings → Payments, then adds the webhook URL `APP_URL/api/payments/razorpay/webhook/<accountId>` with the payment_link.* events in the Razorpay dashboard. Shopify: set `SHOPIFY_API_KEY`, `SHOPIFY_API_SECRET` (and optionally `SHOPIFY_SCOPES`), set the app URL and redirect `APP_URL/api/integrations/shopify/callback` in the Partner Dashboard, and register the mandatory GDPR webhooks (customers/data_request, customers/redact, shop/redact) to `APP_URL/api/integrations/shopify/webhooks`; data requests are recorded for a manual reply. WooCommerce: each store connection shows a delivery URL and secret to paste into WooCommerce → Settings → Advanced → Webhooks.

Inbox premium (Phase 5): migration `20261102120000_inbox_premium` is additive (constant-default columns; the conversations backfill runs with the outbox and updated_at triggers disabled, so it neither floods realtime nor reorders the inbox) and adds conversation_notes, routing_rules, workspace_inbox_settings, notification_preferences, notification_email_queue, saved_filters, quick_reply_favourites and media-library columns, all FORCE RLS. It installs the `conversation_lifecycle` BEFORE trigger on conversations (keeps lifecycle_state, resolved_at and reopened_count consistent with status and assignment) and `messages_first_response` (stamps first_responded_at); the browser cannot write those columns, so resolve/reopen only writes status. Migration `20261102120500_messages_search_index` is a single `CREATE INDEX CONCURRENTLY messages_search_idx` (GIN over `to_tsvector('simple', content_text)`): it runs outside a transaction and keeps messages readable and writable while it builds, which can take a while on a large table. If a deploy is interrupted mid-build, PostgreSQL leaves an INVALID index: run `DROP INDEX CONCURRENTLY messages_search_idx`, mark the migration rolled back (`prisma migrate resolve --rolled-back 20261102120500_messages_search_index`) and deploy again. The worker's scheduling loop (every 30 s) queues `inbox.sla_check` every minute and `inbox.auto_resolve` every five minutes per workspace that has inbox automation configured, deduplicated per time slot; routing queues `inbox.reassign` per conversation with the rule's delay; `inbox.notification_digest` runs at most once per workspace per 30 minutes (checked every five minutes) and claims entries before sending, so a retry never re-sends. The email digest needs `SMTP_URL` (plus `AUTH_EMAIL_FROM`) and `APP_URL`; without them nothing is queued for sending and the email option is shown as unavailable. Internal notes are never sent to WhatsApp, and their realtime events carry ids only (the panel re-reads notes through its route). Phone masking is a display rule for agents and viewers an admin flags: numbers are masked server-side in CRM reads, realtime events, audience pages and exports, inbox search (last four digits only), and numbers quoted in notification titles/bodies and digest titles. It is not applied to customer-written message text or note text, to numbers inside attachments, or to anything an unmasked teammate copies; sends always resolve the real number server-side. Owners and admins always see full numbers.

Billing and plans (Phase 8): migrations `20261102130000_billing`, `20261102131000_auth_identities`, `20261102131500_auth_session_device`, `20261102132000_teams_permissions`, `20261102132100_audit_logs_created_index`, `20261102133000_billing_lifecycle` and `20261102134500_billing_usage_downgrade` are additive (one mapping: `account_subscriptions.status` 'canceled' becomes 'cancelled'; the routing_rules and notifications CHECKs are widened, every existing row satisfies them). Deploy order: the CI `migrate` job applies them before Railway deploys the code, as for every release; never deploy the code first. Billing stays off (Billing shows "not configured", the webhook answers 404) until `BILLING_RAZORPAY_KEY_ID`, `BILLING_RAZORPAY_KEY_SECRET` and `BILLING_RAZORPAY_WEBHOOK_SECRET` (the platform's own Razorpay account, not a workspace's) are set on the web and worker services. Also set `BILLING_SELLER_STATE_CODE` (the GST state code of the seller, e.g. `29`; it decides CGST+SGST or IGST) and optionally `BILLING_SELLER_NAME`, `BILLING_SELLER_GSTIN`, `BILLING_SELLER_ADDRESS`, `BILLING_TRIAL_DAYS` (0 to 30) and `BILLING_ADDON_PRICES` (JSON add-on packs). Plan prices: create one Razorpay plan per plan and interval (amounts in paise, excluding GST), then either set `BILLING_PLAN_PRICES` to a JSON array of `{plan, interval, amount_minor, provider_plan_id}` and have a platform admin call `PUT /api/billing/admin/prices` with `{"source":"env"}`, or PUT one price at a time; platform admins are the verified emails in `PLATFORM_ADMIN_EMAILS` (comma separated). In the Razorpay dashboard add the webhook `APP_URL/api/billing/webhook` with the secret above and the `subscription.*`, `invoice.paid` and `payment.failed` events (payment.failed is acted on only when the payment names its subscription; otherwise subscription.pending moves the workspace to past_due). The worker runs `billing.lifecycle_sweep` every 30 minutes for workspaces with a due transition or an unconfirmed provider call, sends billing notices by email when SMTP is configured, and archives (never deletes) segments, lists, active flows and automations beyond a new plan's limits when a downgrade or cancellation takes effect, restoring them when the limits allow again. Migration `20261102132100_audit_logs_created_index` is a single `CREATE INDEX CONCURRENTLY audit_logs_account_created_idx` (the audit log viewer's keyset index), so audit_logs inserts are never blocked while it builds. If a deploy is interrupted mid-build, PostgreSQL leaves an INVALID index: run `DROP INDEX CONCURRENTLY audit_logs_account_created_idx`, then `prisma migrate resolve --rolled-back 20261102132100_audit_logs_created_index`, and deploy again. The sweep also fetches the provider's state for an `active` subscription whose `current_period_end` passed more than one day ago (`RENEWAL_ALLOWANCE_MS`; the SQL interval in `crm_accounts_for_billing_sweep` must match it), so a lost renewal, halted or cancelled webhook cannot leave a workspace on a paid plan indefinitely. Plan limits: `20261102130000_billing` adds `ai_messages`, `monthly_active_contacts`, `storage_bytes` (bytes) and `whatsapp_numbers` to every plan as unlimited (JSON null), so no existing workspace on free, basic or pro is refused anything at deploy. The gates and meters are live: AI generation checks `ai_messages` per IST month, member uploads check `storage_bytes` (only member-uploaded media counts; inbound customer media the worker mirrors to `chat-media` under `account-<id>/inbound/` never counts and is never refused), and connecting an additional WhatsApp number checks `whatsapp_numbers` (connected numbers and ones mid-setup count; a removed number frees its slot; saving or reconnecting a number the workspace already has is never limited, and nothing is disconnected when a limit is lowered). There is no admin route for limits; once the owner confirms values, set them per plan in the `plans` table as the migration owner, for example `UPDATE plans SET limits = limits || '{"ai_messages":100,"storage_bytes":1073741824,"whatsapp_numbers":1}'::jsonb WHERE id = 'free';` (repeat for `basic` and `pro`; enterprise stays unlimited; set a key back to `null` for unlimited). A new limit applies at once to every workspace on that plan, including those already over it (they keep what they have but cannot add more), so first list the affected workspaces with `SELECT account_id, status FROM account_subscriptions WHERE plan_id = 'free';` and compare their usage on Settings, Plan & usage. Add-ons raise a finite limit only: while `ai_messages` or `whatsapp_numbers` is unlimited on a plan, leave the `ai_messages` and `extra_numbers` packs out of `BILLING_ADDON_PRICES`, or a workspace pays for nothing. Workspaces without a subscription row remain unrestricted (enterprise). Google sign-in: set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from a "Web application" OAuth client whose authorised redirect URI is `APP_URL/api/auth/google/callback`; without them the Google button is hidden.

AI agents (Phase 7): migration `20261103100000_ai_agents` is additive (agent profile, knowledge sources, unanswered questions and the new knowledge-document columns `source_id`, `source_url`, `content_hash`, `fetched_at`, which browsers can read but never write); the CI `migrate` job applies it before Railway deploys the code. Website and sitemap sources are crawled by the worker job `ai.crawl_source` in time-boxed slices (about 40 seconds each, continued as new jobs; a run older than 30 minutes is treated as stale): it stays on the start URL's exact host and its www/apex twin (never sibling subdomains such as other apps on a shared host), honours robots.txt (a `BodhinoxBot` group, else `*`, including Crawl-delay up to 5 seconds), connects only to public addresses on the default ports (every connection and each of at most three redirects is re-checked against private and reserved ranges), fetches two pages at a time, and caps pages at the source's page limit (default 50, at most 500), page bodies at 2 MB and sitemaps at 5 MB. A workspace may have 50 sources. Uploads accept PDF, DOCX, text and Markdown up to 10 MB (PDFs up to 300 pages, at most 300,000 characters of text, DOCX archives up to 60 MB unpacked). Semantic search needs the workspace's own AI embeddings key (Settings, AI); without it knowledge is indexed for keyword search only, and Re-index rebuilds embeddings once a key is saved. Questions the agent could not answer are recorded (worker role) in Learnings; agents answer or dismiss them, and admins promote an answer into the knowledge base as a learned document. The AI Reply flow step answers from the knowledge base under one outbound intent per turn, re-checks the 24-hour window and the bot pause before sending, and leaves by its Handoff port when AI is not set up, the plan's AI messages are used up, a handoff keyword matches, or the answer is not confident. The flow generator and the campaign assistant only create drafts: they never activate a flow or send a campaign. No new environment variables are required.

## Operations

Inspect failed jobs by ID, type, attempts and sanitized last_error through a trusted operator database session. Inspect inbound_action_steps and outbound_intents for interrupted external actions. Do not reset unknown/dispatching intents or stage checkpoints and resend blindly. First reconcile the provider's delivery state and application audit records.

Rotate RSA signing keys with a new AUTH_JWT_KID. Retired public keys remain configured only for the bounded 15-minute access-token overlap described in authentication-validation.md; keep refresh revocation and current-membership checks enabled.

For account defaults run `npm run db:seed -- ACCOUNT_UUID EXISTING_OWNER_USER_UUID` after verified owner onboarding. It is idempotent and does not create demo contacts or send any message. Email-provider setup is explicitly deferred; no live-email success is implied by database authentication tests.
